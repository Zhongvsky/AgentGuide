## 一、 核心知识点与架构心智模型

在 Naive RAG 中，最致命的瓶颈在于**直接拿用户的原始短句去向量库检索**（疑问句与陈述句在向量空间存在流形割裂与词汇鸿沟）。本节实战了 Advanced RAG 最关键的前置模块 **Query Transformation**：

1. **Multi-Query（多路查询重写）**：
   - **空间本质**：高维向量空间的多点采样覆盖（Convex Hull Sampling）。
   - **工程流向**：LLM 生成 3~4 个同义/多视角 Query -> 批量向量化 -> 多路检索 -> Max-Score 并集去重 -> 截取 Top-K。
   - **核心价值**：显著提升**召回率（Recall）**，防止用户因口语化或漏词而遗漏关键条款。

2. **HyDE（Hypothetical Document Embeddings，假设性文档嵌入）**：
   - **空间本质**：跨流形跃迁（从 Question Manifold 跃迁到 Document Manifold），实现 **Doc-to-Doc 密集检索**。
   - **无监督对齐原理**：密集 Embedding 模型判断相似度主要依靠文体句式、领域特征词和语域（Register）。即使 LLM 脑补的假想事实包含轻微错误，其公文句式特征依然能在向量空间与真实规章高度对齐。

## 三、 实战踩坑与工业级排错记录

1. **`sorted()` 升序/降序陷阱**：
   - *现象*：初版 Multi-Query 得分反常暴跌（0.53/0.56），甚至召回了无关的“第二十八条”。
   - *根因*：Python 的 `sorted()` 默认升序（从小到大排序），导致 `[:top_k]` 截取出的实际上是**全场得分最低的倒数 Top-3 分块**！
   - *解决*：必须显式指定 `reverse=True`。

2. **去重字典覆盖逻辑漏洞（低分覆盖高分）**：
   - *现象*：当多路 Query 命中同一个分块时，最终得分不稳定。
   - *根因*：`if ... and score > old_score: ... else:` 分支中，当 `score <= old_score` 时误跌入 `else` 分支，重新构造了低分对象覆盖了原本的高分。
   - *解决*：严格使用 `if chunk_id not in map: ... elif score > old_score: ...` 分离逻辑。

3. **相邻字符串字面量拼接隐患**：
   - *现象*：Prompt 字符串相邻行无空格时，Python 自动拼接为 `regulationsBased`、`regulationwithout`。
   - *解决*：多行 Prompt 行尾统一加 `\n` 或显式标点符号。

4. **Windows GBK 控制台编码崩溃**：
   - *现象*：打印特殊符号 `↳` (`\u21b3`) 导致 `UnicodeEncodeError: 'gbk' codec can't encode...`。
   - *解决*：脚本入口统一注入 `sys.stdout.reconfigure(encoding="utf-8")` 防御。

## 四、 面试级追问与架构思考

### Q1：如果生产环境 QPS 很高，无法容忍每次检索多做一次 LLM 改写（增加数百毫秒到数秒延迟），你会如何设计架构？
- **回答要点**：
  1. **分级路由（Query Complexity Routing）**：先用轻量分类器（或 FastText/小正则/微调的小型 BERT）判断查询是否为复杂/模糊意图。对简单直接问题直走 Naive/缓存；仅对低置信度或模糊查询触发改写。
  2. **异步投机检索（Speculative Retrieval）**：原始 Query 先行发起检索并流式出字；后台并发执行 Multi-Query 改写，如果改写后的置信度显著优于原检索结果，再动态插入补充证据块。
  3. **语义缓存（Semantic Cache）**：使用 Redis/GPTCache 对高频用户的改写结果做语义向量缓存，降低重复 Query 的 LLM 调用率。
  4. **小模型专门化蒸馏**：不调用 7B/70B 通用大模型改写，而是用微调后的 0.5B/1.5B 蒸馏模型专门执行单任务 Query 改写，将推理延迟压制在 50ms 以内。

### Q2：如何量化评估 Query 改写带来的“正向收益”与“负向漂移（Negative Transfer）”？
- **回答要点**：
  1. **构建 Benchmark 金标准集**：准备一批包含「原始 Query、标注的标准 Ground-Truth 依据段落」的测试集。
  2. **量化指标拆解**：
     - **MRR@K（平均倒数排名）与 Hit Rate@K**：评估核心段落排名的绝对提升；
     - **正向增益率（Win Rate）**：改写后 Rank(GT) 提升的 Query 占比；
     - **负向漂移率（Regression Rate）**：改写后原本命中但反而在 Top-K 掉落甚至丢失的 Query 占比。
  3. **质量兜底机制**：在融合检索中，原始 Query 的权重必须高于衍生 Query（如原始权重 1.0，改写权重 0.5~0.7），防止衍生 Query 将向量检索带偏。
